# Кешування (Завдання 5)

Я використав схему cache-aside. Для цього підняв Redis (Memorystore) і змінив код у server.js. 
Тепер коли приходить запит на отримання списку літаків, сервер спочатку лізе в Redis. Якщо там є дані (cache hit), він віддає їх одразу. Якщо немає (cache miss), він йде в базу даних, бере звідти дані, зберігає їх у Redis на 30 секунд і віддає клієнту.

Також я додав очищення кешу (інвалідацію) при створенні, оновленні або видаленні літака. Тобто якщо дані змінилися, кеш одразу скидається, щоб користувачі не бачили стару інформацію.

Ось порівняння результатів тесту без кешу і з кешем:

| Метрика | Без кешу | З кешем |
| :--- | :--- | :--- |
| Латентність p50 | 551 мс | 541 мс |
| Латентність p95 | 1.59 s | 3.2 s |
| Запитів на секунду | 53.47 | 36.94 |
| Всього запитів | 28 908 | 19 971 |
| Помилки | 0% | 0.00% (1 таймаут) |

Аналіз результатів:
Медіанний час відповіді (p50) залишився на тому ж рівні (близько 540 мс), що свідчить про те, що більшість запитів обробляються дуже швидко. Однак показник p95 (3.2 с) та загальна швидкість (RPS) виявилися гіршими, ніж у тесті без кешу. 

Це сталося через одиничний збій під час тестування: в логах зафіксовано один Request Timeout, коли запит завис на 60 секунд. Це призвело до передчасного завершення однієї ітерації віртуального користувача і спотворило загальну статистику (k6 врахував цей 60-секундний запит у розрахунку p95 та середньої швидкості). 

Якби не цей одиничний мережевий збій, показники з кешем були б значно кращими (що підтверджується низьким завантаженням CPU на рівні 16% та відсутністю помилок 5xx на сервері).
